## 1. System Architecture Overview

```
Frontend (React + Vite) → Backend (Express API) → Database (MongoDB) → AI (Groq)
    Port 5173                Port 4000              Port 27017         External API
```

**Components:**
- **Frontend**: React app with React Router, Context API, React Query
- **Backend**: Express API with modular architecture (controllers, services, models)
- **Database**: MongoDB (main) + optional MySQL/PostgreSQL for queries
- **AI**: Groq API using Llama 3.1 model

## 2. Frontend Flow

### 2.1 Application Startup
1. React app mounts to DOM
2. React Query provider enables server state caching
3. React Router enables navigation
4. AuthProvider checks for existing session
5. ToastProvider enables notifications

### 2.2 Authentication State
1. App loads → AuthProvider initializes
2. Calls backend to refresh session
3. If valid token exists → sets user as logged in
4. If invalid → clears user state
5. Shows loading state during check

### 2.3 Making API Requests
1. Frontend calls API function (e.g., api.post("/auth/login"))
2. API client adds access token to Authorization header
3. Request includes credentials for cookies (refresh token)
4. Sends request to backend
5. Handles errors automatically
6. Returns data or throws error

## 3. Backend Flow

### 3.1 Server Startup
1. Connect to MongoDB database
2. Configure Passport for Google OAuth
3. Apply security middleware (Helmet, CORS)
4. Apply logging middleware (Morgan)
5. Apply body parsing middleware
6. Apply cookie parsing middleware
7. Set up all routes under /api/v1
8. Start listening on port 4000

### 3.2 Middleware Order (Important!)
1. Security headers (Helmet)
2. CORS configuration
3. Request logging (Morgan)
4. JSON body parsing
5. Cookie parsing
6. Routes
7. Error handlers

**Why order matters**: Each middleware processes request in sequence. Security first, then parsing, then routes, then errors.

## 4. Authentication Flow

### 4.1 User Registration
1. User submits registration form (name, email, password)
2. Frontend sends POST request to /auth/register
3. Backend receives request in auth controller
4. Controller calls auth service
5. Service checks if email already exists in database
6. Service hashes password using SHA-256
7. Service creates new user in MongoDB
8. Service creates default organization for user
9. Service generates JWT tokens:
   - Access token (15 minutes, short-lived)
   - Refresh token (7 days, long-lived)
10. Controller sets refresh token in httpOnly cookie
11. Controller returns access token and user data as JSON
12. Frontend stores access token in localStorage
13. Frontend updates auth state to logged in

### 4.2 User Login
1. User submits login form (email, password)
2. Frontend sends POST request to /auth/login
3. Backend checks if user exists in database
4. Backend hashes input password and compares with stored hash
5. If match → generate JWT tokens
6. Set refresh token in httpOnly cookie
7. Return access token and user data
8. Frontend stores access token and updates state

### 4.3 Token Refresh (Why Two Tokens?)
**Access Token:**
- Short-lived (15 minutes)
- Sent in Authorization header: "Bearer <token>"
- Used for API calls
- If stolen, limited damage (only 15 minutes)

**Refresh Token:**
- Long-lived (7 days)
- Stored in httpOnly cookie (JavaScript cannot access)
- Used to get new access token when expired
- More secure (protected from XSS)

**Refresh Flow:**
1. Access token expires
2. Frontend calls /auth/refresh
3. Backend checks refresh token in cookie
4. If valid → generates new access token
5. Returns new access token
6. Frontend updates stored token

### 4.4 Protected Routes
1. User tries to access protected route (e.g., /app)
2. Backend middleware checks Authorization header
3. Extracts token from "Bearer <token>"
4. Verifies token with JWT secret
5. If valid → attaches user info to request
6. Allows request to proceed
7. If invalid → returns 401 error

### 4.5 Google OAuth Flow
1. User clicks "Sign in with Google"
2. Frontend redirects to /auth/google
3. Backend redirects to Google consent screen
4. User authorizes app on Google
5. Google redirects back to /auth/google/callback
6. Backend exchanges code for user profile
7. Backend checks if user exists in database
8. If not → creates new user with Google ID
9. Generates JWT tokens
10. Sets refresh token in cookie
11. Redirects to frontend with access token in URL
12. Frontend stores token and updates state

## 5. Database Connection Flow

### 5.1 Connection Validation
1. User enters database credentials (host, port, database, user, password)
2. Frontend sends connection test request
3. Backend validates database type (must be mysql, postgresql, mongodb, or sqlite)
4. Backend validates required fields (host, port, database)
5. Backend attempts to connect to database with 5-second timeout
6. If successful → lists tables/collections
7. If failed → returns error message
8. Returns success/failure to frontend

### 5.2 Supported Databases
- **MySQL**: Uses mysql2 library, connects with credentials
- **PostgreSQL**: Uses pg library, connects with credentials
- **MongoDB**: Uses Mongoose, connects with connection string
- **SQLite**: File-based, no connection test needed

## 6. Query Execution & Encryption Flow

### 6.1 Query Validation (Security First)
1. User submits SQL query
2. Backend checks for dangerous keywords (DROP, DELETE, TRUNCATE, ALTER, etc.)
3. Backend ensures query starts with SELECT (read-only)
4. Backend checks for comment injection (--, /*)
5. If any check fails → returns error
6. If all pass → proceeds to execution

**Why validate?**
- Prevent SQL injection attacks
- Prevent accidental data deletion
- Ensure read-only access
- Protect database integrity

### 6.2 Query Execution
1. Backend connects to database using stored credentials
2. Backend executes the validated query
3. Backend fetches results
4. Backend closes database connection
5. Returns raw data to encryption layer

### 6.3 Data Encryption (AES-256-GCM Explained Simply)

**What is AES-256-GCM?**
- Military-grade encryption standard
- 256-bit key (very secure)
- GCM mode provides encryption + authentication
- Like a digital safe with a tamper-evident seal

**How Encryption Works (Per Key-Value Pair):**

**Step 1: Generate Random IV (Initialization Vector)**
- IV is a random 16-byte number
- Like rolling dice before locking the safe
- Same value encrypted 100 times = 100 different results
- Prevents attackers from seeing patterns

**Step 2: Encrypt with AES-256-GCM**
- Takes three inputs: key, IV, data
- Runs through encryption algorithm
- Produces encrypted data

**Step 3: Generate Authentication Tag**
- Automatically generated during encryption
- Like a wax seal on an envelope
- If someone changes the data, the tag won't match
- Decryption will fail if tampered

**Step 4: Store All Three Parts**
- IV (public, not secret)
- Auth tag (for integrity check)
- Encrypted data (the actual encrypted value)

**Example:**

**Before Encryption:**
```javascript
{
  name: "John Doe",
  email: "john@example.com",
  salary: 75000
}
```

**After Encryption:**
```javascript
{
  name: {
    iv: "random-16-bytes",
    authTag: "integrity-check",
    data: "encrypted-string"
  },
  email: {
    iv: "different-random-bytes",
    authTag: "different-integrity-check",
    data: "different-encrypted-string"
  },
  salary: {
    iv: "another-random-bytes",
    authTag: "another-integrity-check",
    data: "another-encrypted-string"
  }
}
```

**Key Points:**
- Every field has different IV (random)
- Every field has different auth tag
- Every field has different encrypted data
- Same value encrypts differently each time

### 6.4 Creating Analysis Data (Hashed for AI)

**Why Hash Instead of Encrypt for AI?**
- Encrypted data: Cannot be analyzed (random-looking)
- Hashed data: Same value = same hash (patterns visible)
- AI can see patterns without seeing real values

**How Hashing Works:**
- Takes value + secret key
- Runs through HMAC-SHA256 algorithm
- Produces fixed-length hash (16 characters)
- Same input always produces same output (deterministic)

**Example:**
- "john@example.com" → "a1b2c3d4e5f6g7h8"
- "john@example.com" → "a1b2c3d4e5f6g7h8" (same!)
- "jane@example.com" → "b2c3d4e5f6g7h8i9" (different)

**What AI Can See:**
- How many times "john@example.com" appears
- Patterns in data
- Relationships between fields
- But NOT the actual email addresses

### 6.5 Encryption vs Hashing Comparison

| Feature | Encryption | Hashing |
|---------|-----------|----------|
| Reversible | Yes (with key) | No (one-way) |
| Purpose | Data confidentiality | Pattern analysis / integrity |
| Same input | Different output each time | Same output (deterministic) |
| Use case | Storage, transmission | AI analysis, passwords |

## 7. AI Processing Flow

### 7.1 Sending Data to AI
1. Backend prepares messages for AI:
   - System prompt: "You are a SaaS analytics assistant"
   - User prompt: workspace context + hashed data + question
2. Backend sends request to Groq API
3. Groq processes with Llama 3.1 model
4. AI analyzes patterns in hashed data
5. AI generates business insights
6. AI returns text answer

### 7.2 AI Configuration

**Temperature (0.2):**
- Controls randomness/creativity
- 0.0-0.3: More deterministic (consistent answers)
- 0.7-1.0: More creative (varied answers)
- Use 0.2 for business analytics (want consistency)

**Max Tokens (700):**
- Limits response length
- Controls cost (pay per token)
- Prevents overly long responses

**System Prompt:**
- Defines AI's persona
- Guides AI's behavior
- "You are a SaaS analytics assistant"
- Ensures business-focused answers

### 7.3 AI Response Handling
1. Backend receives AI response
2. Extracts answer text
3. Extracts token usage (for cost tracking)
4. Logs usage to database
5. Returns answer to frontend
6. Frontend displays answer to user

## 8. API Key Authentication & Quota Flow

### 8.1 API Key Authentication
1. Widget sends request with API key in header
2. Backend extracts API key from request
3. Backend hashes API key with SHA-256
4. Backend looks up hashed key in database
5. If found and active → attach organization/workspace to request
6. If not found or inactive → return 401 error

**Why Hash API Keys?**
- Never store raw keys in database
- If database is hacked, keys are still safe
- SHA-256 is one-way (cannot reverse to get original key)
- Compare hashes, not raw values

### 8.2 Quota Checking
1. Backend gets organization's quota from database
2. Checks if quota exceeded for request type
3. If not exceeded → increment counter
4. If exceeded → return 429 (Too Many Requests) error
5. Save updated quota to database

**Quota Types:**
- API requests: 1000 per organization
- Queries: 100 per organization
- Reports: 10 per organization

**Why Quotas?**
- Prevent abuse
- Control costs
- Fair usage across users
- Plan-based limits

## 9. Complete End-to-End Flow (Widget Query)

```
1. User asks question via widget
   ↓
2. API key authentication
   - Extract API key from header
   - Hash with SHA-256
   - Lookup in database
   - Verify active status
   ↓
3. Quota checking
   - Get organization quota
   - Check if limit exceeded
   - Increment counter if not
   ↓
4. Query validation (if SQL provided)
   - Check for dangerous keywords
   - Ensure SELECT only
   - Prevent comment injection
   ↓
5. Execute query (if SQL provided)
   - Connect to database
   - Run query
   - Fetch results
   ↓
6. Encrypt all data
   - For each row and field:
     - Generate random IV
     - Encrypt with AES-256-GCM
     - Generate auth tag
     - Store { iv, authTag, data }
   ↓
7. Create analysis data (hashed)
   - For each row and field:
     - Generate HMAC-SHA256 hash
     - Same value = same hash
   ↓
8. Send to AI (Groq)
   - System prompt: persona
   - User prompt: context + hashed data + question
   - Temperature: 0.2 (consistent)
   - Max tokens: 700 (cost control)
   ↓
9. AI response
   - Analyzes patterns in hashed data
   - Generates business insights
   - Returns text answer
   ↓
10. Log usage
    - Organization, workspace, API key
    - Query text, tokens used
    - Response time, success/failure
    ↓
11. Return response
    - AI answer (text)
    - Indicate encrypted data exists (server-side only)
```

## 10. Decryption Flow (Authorized Users Only)

```
1. Authorized user requests data
   - Must be owner or admin role
   - Additional authentication required
   ↓
2. Retrieve encrypted data
   - Fetch from server-side storage
   - Verify user authorization
   ↓
3. Decrypt data
   - For each row and field:
     - Extract IV and auth tag
     - Decrypt with AES-256-GCM using key
     - Verify auth tag (integrity check)
     - Return original value
   ↓
4. Return decrypted data
   - Send original data to authorized user
   - Log decryption event for audit trail
```

**Why Only Authorized Users?**
- Encrypted data never leaves server
- Only privileged users can request decryption
- Audit trail tracks who accessed what
- Complies with data privacy regulations

## 11. Interview Questions

### Architecture & Project Structure

**Q: How is your project structured?**
A: Monorepo with npm workspaces. Two main apps: frontend (React + Vite) and backend (Express). Shared root for dependencies.

**Q: Why use a monorepo?**
A: Shared dependencies, consistent tooling, easy to run both apps with one command, better organization.

**Q: What build tools do you use?**
A: Frontend uses Vite (fast hot reload, optimized builds). Backend doesn't need build step (Node.js runs directly).

---

### Frontend (React)

**Q: How do you manage state in React?**
A: Three layers: Context API for global state (auth, toast), React Query for server state (caching, refetching), useState for local component state.

**Q: Why Context API instead of Redux?**
A: Simpler for this use case, built into React, sufficient for auth and toast. Redux would be overkill.

**Q: What is React Query and why use it?**
A: Server state management library. Handles caching, refetching, loading states automatically. Reduces boilerplate and improves UX.

**Q: How does React Router work?**
A: Client-side routing. BrowserRouter handles URL changes. ProtectedRoute component checks auth before allowing access. useNavigate for programmatic navigation.

---

### Backend (Express)

**Q: Explain your backend architecture.**
A: Modular MVC pattern. Models define database structure. Services contain business logic. Controllers handle HTTP requests. Routes map URLs to controllers. Middlewares handle cross-cutting concerns.

**Q: Why use Express.js?**
A: Minimal, flexible, large ecosystem, easy to set up REST APIs, good performance.

**Q: What middleware do you use and why?**
A: Helmet (security headers), CORS (cross-origin requests), Morgan (logging), cookie-parser (cookies), express.json (parse JSON bodies).

**Q: How do you handle errors?**
A: Centralized error middleware. Custom ApiError class. Try-catch in controllers. Use next(err) to pass to error handler.

---

### Authentication & Authorization

**Q: Explain your authentication flow.**
A: JWT tokens (access + refresh). Access token (15min) in Authorization header. Refresh token (7days) in httpOnly cookie. Token refresh on app load. Protected routes with middleware.

**Q: Why two tokens instead of one?**
A: Access token is short-lived for security. If stolen, limited damage (15min). Refresh token is long-lived for convenience, stored in httpOnly cookie (protected from XSS).

**Q: How do you secure passwords?**
A: Hash with SHA-256 before storing. Never store plain text. Compare hashes during login. (Note: bcrypt is better for production).

**Q: What is Passport.js?**
A: Authentication middleware for Node.js. We use it for Google OAuth. Handles OAuth flow (redirect to Google, callback). Stateless with JWT (session: false).

**Q: How does Google OAuth work?**
A: User clicks "Sign in with Google" → redirect to Google → user authorizes → Google redirects back with code → exchange code for profile → create/find user → generate tokens → redirect to frontend.

---

### Database (MongoDB)

**Q: Why MongoDB?**
A: Flexible schema (JSON-like documents), good for SaaS, easy to scale horizontally, Mongoose ODM for validation.

**Q: Explain Mongoose schemas.**
A: Define data structure and validation. Types like String, Number, ObjectId. Required fields, unique constraints. Indexes for performance. Timestamps for tracking.

**Q: How do you handle relationships?**
A: ObjectId references. Population with .populate(). Example: User → Organization → Workspaces.

**Q: How do you connect to SQL databases?**
A: MySQL with mysql2 library, PostgreSQL with pg library. Connection testing with timeout. Execute queries dynamically.

---

### API Key Authentication

**Q: How do API keys work?**
A: Generated per workspace. SHA-256 hashed before storage. Sent in x-api-key header. Verified on each request. Can be revoked (isActive flag).

**Q: Why hash API keys?**
A: Never store raw keys. If database compromised, keys safe. SHA-256 is one-way. Compare hashes, not raw values.

**Q: How do you scope API keys?**
A: Each key linked to organization. Optional workspace restriction. Only access data from that scope. Quota limits per organization.

---

### Quota & Rate Limiting

**Q: How do you implement rate limiting?**
A: Quota per organization. Track API requests, queries, reports. Check before allowing request. Return 429 if exceeded. Increment counter on success.

**Q: What are the default limits?**
A: API requests: 1000, Queries: 100, Reports: 10.

**Q: How do you prevent abuse?**
A: Quota checking, API key authentication, query validation (prevent dangerous SQL), read-only queries only.

---

### Query Validation

**Q: How do you validate SQL queries?**
A: Check for dangerous keywords (DROP, DELETE, etc.). Ensure SELECT only (read-only). Prevent comment injection. Reject if validation fails.

**Q: Why only SELECT queries?**
A: Prevent data modification, protect against accidental drops, ensure read-only access, safer for AI analysis.

**Q: What about SQL injection?**
A: Input validation, restrict allowed keywords, never concatenate user input, use parameterized queries when implemented.

---

### Encryption & Data Masking

**Q: How do you encrypt data before sending to AI?**
A: AES-256-GCM encryption. Random IV per value. Authentication tag for integrity. Encrypt every key-value pair. Store as { iv, authTag, data }.

**Q: What is AES-256-GCM?**
A: Advanced Encryption Standard with 256-bit key. GCM mode provides encryption + authentication. Military-grade security. Auth tag detects tampering.

**Q: Why random IV?**
A: Same value encrypts differently each time. Prevents pattern analysis. IV doesn't need to be secret, just unique.

**Q: What is the auth tag?**
A: 16-byte signature generated during encryption. Verified during decryption. Detects tampering. If data changed, decryption fails.

**Q: How does decryption work?**
A: Extract IV and auth tag. Use same encryption key. Decrypt with AES-256-GCM. Verify auth tag. Return original value.

**Q: What is the difference between encryption and hashing?**
A: Encryption is reversible (with key), hashing is one-way. Encryption for confidentiality, hashing for integrity or pattern analysis.

**Q: Why use hashing for AI analysis?**
A: Same value = same hash (deterministic). AI can see patterns without seeing data. Example: email always hashes to same value. AI can count occurrences but cannot see actual email.

### AI Integration (Groq)

**Q: How do you integrate with Groq AI?**
A: HTTP API calls to Groq. OpenAI-compatible API. Send messages array (system + user prompts). Configure temperature and max tokens.

**Q: What is temperature in AI?**
A: Controls randomness. 0.0-0.3 is more deterministic. 0.7-1.0 is more creative. Use 0.2 for consistent business answers.

**Q: What is the system prompt?**
A: Defines AI persona. "You are a SaaS analytics assistant". Guides AI's behavior. Context for all responses.

**Q: How do you control AI costs?**
A: Max tokens limit (700). Temperature control. Log token usage. Cache responses with React Query.

**Q: What happens if AI fails?**
A: Try-catch in controller. Log failure in usage logs. Return error to user. Don't increment quota on failure.

---

### Security

**Q: How do you prevent XSS attacks?**
A: httpOnly cookies for refresh tokens. Helmet for security headers. Input validation. React handles output sanitization.

**Q: How do you prevent CSRF attacks?**
A: SameSite cookie attribute. CORS configuration. Consider state parameter for OAuth.

**Q: How do you protect sensitive data?**
A: Encrypt before sending to AI. Hash API keys. Hash passwords. Never log sensitive info. Environment variables for secrets.

**Q: What security headers do you use?**
A: Helmet adds: X-Content-Type-Options, X-Frame-Options, X-XSS-Protection, Strict-Transport-Security, Content-Security-Policy.

---

### Performance & Optimization

**Q: How do you optimize database queries?**
A: Indexes on frequently queried fields. Use .select() to limit fields. Aggregate queries for analytics. Connection pooling.

**Q: How do you handle large datasets?**
A: Pagination (limit + skip). Cursor-based pagination for large datasets. Stream results for exports. Lazy loading.

**Q: How do you cache responses?**
A: React Query for frontend. Consider Redis for backend. Cache frequently accessed data. Invalidate on updates.

---

### Deployment & DevOps

**Q: How do you deploy this application?**
A: Docker Compose for local/VPS. Separate containers for web, api, database. Environment variables for configuration. Nginx reverse proxy for production.

**Q: What is in your Docker setup?**
A: Web container (Vite build + static files), API container (Node.js + Express), Database container (MongoDB). Docker Compose orchestrates all.

**Q: How do you manage environment variables?**
A: .env file for local, .env.example as template, server environment variables for production. Never commit .env to git.

---

### Testing

**Q: How would you test this application?**
A: Unit tests for services and utilities. Integration tests for API endpoints. E2E tests for user flows (Cypress/Playwright). Mock external services (Groq, databases).

**Q: How do you test authentication?**
A: Test login with valid credentials, invalid credentials, token refresh, protected routes without token, protected routes with expired token.

---

### Scalability

**Q: How would you scale this application?**
A: Horizontal scaling (multiple API instances), load balancer (Nginx/HAProxy), database replica sets/sharding, Redis for caching and sessions, CDN for static assets.

**Q: How do you handle concurrent requests?**
A: Node.js is non-blocking (event loop). Connection pooling for databases. Queue for heavy operations (reports). Worker threads for CPU-intensive tasks.
